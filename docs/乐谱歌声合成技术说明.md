# 乐谱歌声合成（SVS）技术说明 —— YingMusic-Singer

> 场景：**上传乐谱（MIDI）+ 歌词 + 音色音频 → 生成歌曲文件**
>
> 证据标注：**【实测】** = 在 RTX 3050 Laptop（4 GB 显存）上实测；**【官方】** = 上游文档原文；**【推算】** = 估计值。

---

## 0. 结论

| 问题 | 答案 |
|---|---|
| 能做到吗？ | ✅ 能。用 **YingMusic-Singer V1**（零样本歌声合成），输入正好是乐谱+歌词+音色三样 |
| 4GB 显存够吗？ | ✅ **够，但极紧**：全卡实测峰值 3924 MiB / 4096 MiB，仅剩 172 MiB 余量 |
| 速度 | 27.88 秒音频耗时 50.3 秒（RTF 1.80，NFE 32 步）|
| 音准 | 音高轮廓与乐谱相关系数 **0.868**，但存在 +3.89 半音固定移调，需 `pitch_shift` 校正 |
| 单次长度上限 | 约 45 秒（模型 `max_duration=4096` 帧），整首歌需分段拼接（见 §5）|

**关键机制**：显存不足时 NVIDIA 驱动启用 **sysmem fallback**（显存回退到系统内存），
所以 PyTorch 报告"分配峰值 6335 MiB / 保留 8946 MiB"仍能跑完 —— 代价是速度。

## 1. 它和 Seed-VC 的本质区别

| | Seed-VC（音色转换）| YingMusic-Singer（乐谱唱歌）|
|---|---|---|
| 类型 | SVC 音色转换 | **SVS 歌声合成** |
| 输入 | 必须已有**一段人声演唱** | **乐谱 + 歌词 + 音色音频** |
| 能力 | 换音色，不会唱歌 | 从乐谱"唱"出来，无需现成人声 |
| 长度 | 不限（自动分段） | 单次约 45 秒，更长需分段拼接 |

两者互补：**要"把某首歌换成我的音色"用 Seed-VC；要"用我的音色唱一首新歌（只有谱子）"用 YingMusic-Singer。**

## 3. 修复的 4 个 Windows 卡点（这是能跑通的关键）

### 3.1 flash-attn 硬依赖 → SDPA 回退补丁 ★最关键

**注意**：README 的安装步骤要求 flash-attn（且只给了 Linux 轮子）。
`decoder/modules.py` 里确实有一条 `attention()` 带 SDPA 回退，但 **DiT 的自注意力
并不走它** —— 第 327 行直接调用 `flash_attention()`，并在第 113 行
`assert FLASH_ATTN_2_AVAILABLE` 直接崩溃。

**本地修改**：在 `flash_attention()` 开头加入 PyTorch 原生
`scaled_dot_product_attention` 等价分支（保持 `[B,L,N,C]` 布局，用布尔掩码处理
`k_lens` 补齐位）。因为 `singer.yaml` 未配置 `window_size`（恒为默认 `(-1,-1)`，
即无滑动窗口），所以可完全等价替换。

### 3.2 torchaudio 2.9 的 I/O 依赖 torchcodec + FFmpeg 共享库

`torchaudio.load()` 报 `Could not load libtorchcodec`（部署的是静态 ffmpeg.exe，
没有 torchcodec 需要的 avcodec-*.dll 共享库）。

**本地修改**：`model.py` 的 `load_audio()` 改为优先用 `soundfile` 读取
（soundfile 0.14 自带 libsndfile，支持 wav/mp3/flac/ogg），失败再回退 torchaudio。

### 3.3 espeak-ng 缺失（phonemizer 需要）

报 `RuntimeError: espeak not installed on your system`。

**解决**：安装 PyPI 包 `espeakng-loader`（自带 espeak-ng.dll 与 espeak-ng-data），
并在 site-packages 放一个 `sitecustomize.py` 自动设置：

```python
PHONEMIZER_ESPEAK_LIBRARY   = <...>\espeakng_loader\espeak-ng.dll
PHONEMIZER_ESPEAK_DATA_PATH = <...>\espeakng_loader\espeak-ng-data
```

同时把 DLL 目录加入 PATH。sitecustomize 由解释器启动时自动导入，故对整个 venv 生效。

> 附注：espeak 的语言代码是 `cmn`（普通话）而非 `zh`。仓库内部已正确映射
> （`g2p/__init__.py` 中 `"zh": "cmn"`），无需改动。

### 3.4 LangSegment 0.2.0 自身有 bug

`import LangSegment` 直接失败：其 `__init__.py` 导入了 `LangSegment.py` 中
**不存在**的 `setLangfilters` / `getLangfilters`。PyPI 上仅有 0.2.0 这一个版本。

**本地修改**：把 `__init__.py` 第 1 行的这两个名字删除（仓库只用到
`setfilters` / `getTexts`）。

## 4. 实测数据

### 4.1 性能与显存【实测】

测试条件：官方示例素材（`male.wav` 作音色 + 下等马 MIDI，27.8 秒），NFE 32 步，CFG 4.0。

| 指标 | 数值 |
|---|---|
| 模型加载 | 18.2 秒，权重占 2729 MiB |
| 采样阶段 | 32 步 @ 2.68 it/s ≈ 12 秒 |
| 总推理 | 50.3 秒 |
| 输出 | 27.88 秒 · 48 kHz · 立体声 · PCM_16 |
| RTF | **1.80** |
| 全卡显存峰值 | **3924 MiB / 4096 MiB**（余量 172 MiB）|
| PyTorch 分配/保留峰值 | 6335 / 8946 MiB（超出物理显存 → 驱动回退到系统内存）|

### 4.2 音准验证【实测】

用 `librosa.pyin` 提取生成音频 F0，与 MIDI 的 99 个音符逐一对齐比较：

| 指标 | 数值 |
|---|---|
| 音高轮廓相关系数 | **0.868**（跟随良好）|
| 原始平均绝对误差 | 4.11 半音 |
| 系统性偏移 | **+3.89 半音**（标准差 2.42）|
| 去偏移后残差 MAE | **1.79 半音**（中位数 1.05，43% 音符误差 <1 半音）|

**解读**：误差主要是一个**固定移调**而非随机跑调，说明模型忠实跟随了乐谱轮廓，
只是绝对音区（调性）偏移。官方 README 也提示："若参考音频音域与目标旋律差异较大，
建议手动调整调性"。**用 `pitch_shift` 下调 4 个半音即可对齐。**

### 4.3 输出音频客观特征【实测】

| 指标 | 数值 |
|---|---|
| RMS | 0.250（电平健康）|
| 峰值 | 1.000（贴满刻度）|
| 非静音比例 | 87.4% |
| 8 段能量分布 | 0.204 ~ 0.302（连续，无断裂/静音段）|
| 频谱质心 | 3122 Hz（符合人声特征）|

## 5. 长歌方案：突破单次时长上限（已实装）

### 5.1 上限的真实机制【源码+实测】

README 说"总时长不超过 45 秒"，但那**不是硬限制**：

| 项 | 数值 | 依据 |
|---|---|---|
| VAE/DiT 帧率 | 25 fps（`DEFAULT_VAE_FRAME_HZ = 25`）| 源码 `model.py:59` |
| 硬上限 | `max_duration = 4096` 帧 = **163.8 秒**（含音色 prompt）| 源码 `model.py:415` |
| 旋律可用上限 | 约 **155~158 秒** | 推算 |
| 输出与乐谱的对应 | 输出 = **0.08 秒静音 + 旋律**，旋律长度 = MIDI 时长 × 25 帧 | 实测吻合（±0.01 秒）|

**45 秒是显存/内存的工程建议，不是模型限制。** 在 4 GB 显存上的实测边界：

| 乐谱时长 | 结果 | 显存 |
|---|---|---|
| 27.9 秒 | ✅ 通过 | 峰值约 3900 MiB |
| **40 秒** | ✅ **通过**（耗时 66.5 秒，RTF 1.66）| PyTorch 分配峰值 7625 MiB |
| 55 秒 | ❌ **OOM**（VAE 解码阶段 `snake_beta`）| 已分配 7.78 GiB，再要 1.28 GiB 失败 |

失败点在后端 VAE 解码的激活值。4 GB 显存需要驱动**回退到系统内存**才能支撑，
因此实际可用的上限比理论值更低，且与系统内存大小相关。

### 5.2 分段生成 + 无缝拼接（`long_song.py`）

```
乐谱 ──┬─ 按"音符间隙"切分（默认每段 30 秒，优先切在乐句呼吸处，不截断延音）
       ├─ 歌词按各段音符数比例切分（中文按字、西文按词，标点跟随前字）
       ├─ 逐段用同一音色参考生成
       └─ 采样级精确拼接（去掉每段 0.08 秒引导 → 按起始时间落位 → 交界处 30ms 等功率防咔哒）
```

关键实现细节：

- **切点选在最大音符间隙**（目标点 ±3 秒内搜索），因此接缝大多落在静音处；
- **歌词切分按音符数加权**，而非按时长，因为"一字一音"才是歌词与旋律的对应关系；
- 拼接用**等功率淡化**：相邻段无重叠时只起防咔哒作用（30ms），
  真有重叠时自动退化为标准交叉淡化（实测重叠中心值 1.061 = 理论等功率值）；
- 每段生成后主动 `torch.cuda.empty_cache()`：显存紧张时依赖内存回退，必须及时释放。

### 5.3 整首歌实测【实测】

条件：官方示例乐谱重复 4 遍 = **111.2 秒**，分 4 段（每段 28.3 秒），NFE 32。

| 指标 | 数值 |
|---|---|
| 总耗时 | **198.8 秒**（RTF 1.78）|
| 产出音频 | 111.73 秒（含 0.5 秒尾部留白）|
| 分段耗时 | 47.1 / 48.4 / 47.8 / 53.1 秒 |
| 全卡显存峰值 | 3910 MiB / 4096 MiB |
| 是否 OOM | 否 |

**拼接质量验证**（关键结论）：

| 检查项 | 结果 |
|---|---|
| 拼接点 ±5ms 内最大采样跳变 | **0.0000**（完全无缝）|
| 单段原始输出最大跳变 | 0.7794 |
| 拼接输出最大跳变 | 0.7879 |

大跳变在**单段输出中本来就存在**（模型自身的爆破音），**拼接没有引入任何额外瑕疵**。

### 5.4 调性（pitch_shift）的重要发现【实测】

对同一段素材用不同 `pitch_shift` 生成，在同一最佳对齐偏移（-0.40 秒）下比较：

| pitch_shift | 音高轮廓相关系数 | 系统偏移 | 去偏移残差 |
|---|---|---|---|
| **-1** | **0.887** | +3.66 半音 | 1.64 半音 |
| -4 | 0.455 | -4.13 半音 | 3.21 半音 |

**两个结论**：

1. **`pitch_shift` 不是线性旋钮**：输入只改了 -3 半音，实际音高偏移了 -7.79 半音，
   说明大幅移调会改变模型的音高映射行为。
2. **大幅移调会明显劣化音质**：相关系数从 0.887 掉到 0.455。

因此界面默认值设为官方示例验证过的 **-1**，并提示只在 -3~+2 内微调。
另外各段的系统偏移高度一致（+3.9~+4.1 半音），**分段之间不会跑调**，这对拼接整首歌很关键。

## 6. 集成进念山AI（已完成）

### 6.1 架构：子进程隔离 + 显存互斥

两套环境不兼容（念山AI 是 py3.10 + torch 2.4，YingMusic 需 py3.12 + torch 2.9），
且 4GB 显存装不下两个模型，故采用：

```
念山AI 网页（py3.10 进程，常驻 Seed-VC）
   │
   ├─ 点「音色转换」→ 若 Seed-VC 已卸载则自动重载（约 20 秒）→ 正常转换
   │
   └─ 点「乐谱唱歌」→ ① 卸载 Seed-VC 全部模型并清空显存
                      ② 写 job.json（含歌词，UTF-8）
                      ③ 子进程跑 svs_runner.py（py3.12 环境）
                      ④ 解析子进程 stdout 协议实时刷新进度
```

**子进程输出协议**（stdout 逐行）：

```
PLAN|<乐谱秒数>|<段数>|<音符数>
PROGRESS|<阶段>|<说明>
STATS|<总耗时>|<段数>|<音频秒数>|<音符数>
DONE|<输出wav路径>
ERROR|<错误信息>
```

> 歌词通过 **JSON 文件**传递而非命令行参数——Windows 命令行传中文极易乱码。
> 运行器用 `utf-8-sig` 读取，兼容带/不带 BOM 两种 JSON。

### 6.2 界面

念山AI 现在是双模式（顶部标签页切换）：

| 标签页 | 功能 | 引擎 |
|---|---|---|
| 🎤 音色转换 | 把已有歌曲/人声换成你的音色（可自动分离人声+混音）| Seed-VC |
| 🎼 乐谱唱歌 | 上传 MIDI 乐谱 + 歌词 + 音色 → 生成新歌 | YingMusic-Singer |

「乐谱唱歌」页参数：MIDI、歌词、音色音频（5~7 秒）、**音色片段所唱的词**、
分段长度（15~40 秒）、升降调、CFG、扩散步数。

### 6.3 集成实测【实测】

| 测试 | 结果 |
|---|---|
| 端点注册 | `/convert` + `/svs` 均正常 |
| 乐谱唱歌端到端 | ✅ 76.4 秒产出 28.31 秒歌声，**114 次实时进度刷新** |
| 切回音色转换 | ✅ 自动重载 Seed-VC 并转换成功（总 22.6 秒，含重载约 10 秒）|
| 显存互斥 | ✅ 两个模式不会同时驻留 |

## 7. 已知限制与风险

1. **显存余量仅 172 MiB** —— 靠驱动内存回退才跑通。因此：
   - 不能与念山AI（Seed-VC 常驻约 2.7~3.4 GB）**同时运行**，两者互斥；
   - 后台若有浏览器/游戏等占显存程序，可能失败；
   - 更长的旋律会需要更多回退，速度进一步下降。
2. **单次上限约 45 秒**（`max_duration=4096` 帧）。整首歌需分段生成再拼接（接缝风险）。
3. **音色参考音频 5~7 秒为佳**，且**必须同时提供该片段所唱的词**
   （模型把"参考词 + 目标词"拼成一个文本序列，见 `model.py:674`）。
4. **调性需校正**：`pitch_shift` 默认 0 时会偏高约 4 个半音。
5. 首次运行会在工作目录生成 `jieba.cache`。

## 8. 复现命令

以下均在**上游 YingMusic-Singer 目录内**执行（`install.ps1` 会把本项目的脚本复制进去）：

```powershell
cd <上游目录>\YingMusic-Singer
$env:PYTHONPATH = "$PWD\src"
$env:PYTHONUTF8 = "1"
.\.venv\Scripts\python.exe probe_v1.py      # 完整推理探测
.\.venv\Scripts\python.exe verify_melody.py # 音准验证
```

直接调用命令行（等价于官方 README 用法，增加本地权重路径）：

```powershell
.\.venv\Scripts\python.exe src\singer\model.py `
  --ckpt_path ckpts `
  --timbre_audio_path resources\audios\male.wav `
  --timbre_audio_content "在爱的回归线，又期待相见。" `
  --midi_file "resources\audios\female__Rnb_Funk__下等马_clip_001.mid" `
  --lyrics "..." --out_path outputs\out.wav `
  --cfg_strength 4.0 --nfe_steps 32 --pitch_shift -4
```


整首歌分段合成（等效网页端行为，便于命令行调试）：

```powershell
$env:PYTHONPATH = "$PWD\src"; $env:PYTHONUTF8 = "1"
.\.venv\Scripts\python.exe long_song.py `
  --midi song.mid --lyrics "歌词……" `
  --timbre timbre.wav --timbre-content "参考片段所唱的词" `
  --out outputs\song.wav --chunk 30 --pitch-shift -1 --nfe 32
```

网页端（子进程协议）自测：

```powershell
.\.venv\Scripts\python.exe svs_runner.py job.json
```

`job.json` 字段见文件头注释。分段结果会缓存为 `outputs\chunks\chunk_XX.npy`，
可用 `use_cache=True` 跳过重新推理、只调拼接参数。
