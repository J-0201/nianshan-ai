### 为什么选 Seed-VC

零样本意味着**不用训练就能出结果**，而它的微调门槛低到 4GB 也能承受【官方】：

- 零样本：1~30 秒参考音频直接转换
- 微调：每位说话人**至少 1 条**语音、**最少 100 步**、T4 上 2 分钟

对比之下 RVC 与 so-vits-svc 都需先训练模型，而训练恰是 4GB 最吃力的环节。RVC 官方 FAQ
对此有明确表述【官方】：

> 训练的话缩小 batch size（**如果缩小到1还不够只能更换显卡训练**）……**4G以下显存可以直接放弃，4G显存显卡还有救。**

你的 3050 正好 4096 MiB，踩在官方划定的分界线上——所以本方案走零样本路线。

### 2.3 依赖安装的取舍

官方 `requirements.txt` 需要三处处理【实测】：

1. **删掉前 3 行**——它们指向 `download.pytorch.org/whl/nightly/cu126`，本机不可达，且会覆盖正确版本。
2. **删掉 `torch`/`torchvision`/`torchaudio` 三行**——避免 uv 从 PyPI 抓 CPU 版覆盖 CUDA 版。
3. **删掉 `resemblyzer`**——它依赖需要 C 编译的 `webrtcvad`，是 Windows 上最常见的失败点。
   经代码核查，它**只被 `eval.py` 用到**，推理流程完全不需要。

处理后的清单保存为 `requirements-infer.txt`。

### 2.4 修复的上游 bug

**`torchaudio.compliance.kaldi.fbank` 在 CUDA 上崩溃**【实测】：

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xc0 in position 117: invalid start byte
```

报错位置在 `torch.fft.rfft` 内部，看起来像 FFT 问题，实际不是。逐项界定后：

| 操作 | CPU | CUDA |
|---|---|---|
| `torch.fft.rfft` | 正常 | **正常** |
| `torch.fft.fft` | 正常 | **正常** |
| `torch.stft` | 正常 | **正常** |
| `kaldi.fbank` | 正常 | **崩溃** |

结论：不是 CUDA FFT 的问题，而是 fbank 这条路径上的问题。该 `UnicodeDecodeError`
很可能是把底层错误信息按 UTF-8 解码失败后抛出的"伪装错误"。

**处理**：`svc_launch.py` 把 fbank 强制放到 CPU 计算再搬回设备。fbank 只用于给 campplus
提取 80 维梅尔特征，计算量极小，对结果无影响，且不改动上游代码（便于日后 `git pull`）。

## 3. 踩坑记录（这些是本机能跑通的关键）

### 3.1 conda 装不上：国内镜像会拒绝海外出口 IP

最初用 conda + 清华源创建环境，失败于 SSL 中断。诊断发现：

| 源 | 规则模式 | 全局模式（海外出口）|
|---|---|---|
| 清华 PyPI / conda | 正常 | **403 拒绝** |
| SJTU pytorch-wheels | 正常 | TLS 握手中断 |
| anaconda 官方 | 正常 | 正常 |
| GitHub | **不通** | 通 |

**结论**：镜像可用性与代理模式强相关。全球化模式会让国内镜像拒服（403）。
最终**绕开 conda，改用 `uv`**，它从 GitHub 拉独立 CPython，不受镜像策略影响。

### 3.2 hf-mirror 无法下载 LFS 大文件

`HF_ENDPOINT=https://hf-mirror.com` 是官方 README 推荐的方案【官方】，但对本项目**不可用**【实测】：

- hf-mirror 把 LFS 大文件重定向到 `cas-bridge.xethub.hf.co` → **403**，huggingface_hub
  取不到元数据，报 `Distant resource does not seem to be on huggingface.co`
- 真实 huggingface.co 的重定向目标是 `us.aws.cdn.hf.co` → **可达**

**解法**：把 HF 流量单独走本地代理（`HTTPS_PROXY=http://127.0.0.1:7897`）直连真实 HF，
实测下载速度 **5.9 MB/s**。`run_svc.ps1` 已内置此逻辑，并在代理不可用时自动退回镜像。

### 3.3 权重文件名与 README 不一致

README 写的是 `DiT_seed_v2_uvit_whisper_base_f0_44k_bigvgan_pruned_ft_ema.pth`，
而**代码实际请求的是带 `_v2` 后缀**的版本【实测】：

```
DiT_seed_v2_uvit_whisper_base_f0_44k_bigvgan_pruned_ft_ema_v2.pth   (820 MB)
```

另外**代码还会额外下载**一个 README 未提及的依赖：

```
lj1995/VoiceConversionWebUI  →  rmvpe.pt   (音高提取器，歌声转换必需)
```

完整下载清单（共 2371 MB）：

| 仓库 | 文件 | 用途 |
|---|---|---|
| `Plachta/Seed-VC` | DiT_..._v2.pth + config yml | 主模型 |
| `nvidia/bigvgan_v2_44khz_128band_512x` | 声码器 | 波形重建 |
| `openai/whisper-small` | 语义分词器 | 内容编码 |
| `lj1995/VoiceConversionWebUI` | rmvpe.pt | 音高提取 |
| `funasr/campplus` | campplus_cn_common.bin | 说话人嵌入 |

### 3.4 其他

- **输出是 32 位浮点 WAV**（subtype FLOAT），Python 标准库 `wave` 读不了，需用 `soundfile`。
- **缓存要重定向**：transformers 默认写 C 盘，本机 C 盘仅剩 54GB，脚本已改到 F 盘。
- **PowerShell 脚本必须带 UTF-8 BOM**：否则含中文的 .ps1 会被按 ANSI 解析而语法报错。
- **必须在项目目录内启动网页应用**：`app_svc.py` 用的是相对路径
  （`'./checkpoints/hf_cache'`、界面示例 `examples/source/...`）。若在别的目录启动，
  会把 **1.4GB 权重重新下载到错误位置**，示例音频也加载不出来。`run_webapp.ps1` 已固定 `Set-Location`。
- **路径含空格时不能用 `Start-Process -ArgumentList`**：`F:\ai music\...` 会在空格处被拆开，
  python 会去开 `F:\ai` 而报 `No such file or directory`。脚本内用 `&` 调用可避免。
- **PowerShell 解析 JSON 会出错**：`gradio /config` 里有 PowerShell 无法处理的属性名，
  验证脚本改用 Python 解析。
- **调 Gradio API 时，文件入参必须是字典**：不能直接传路径字符串，否则报
  `The 'meta' field must be explicitly provided`。正确格式是
  `{"path": ..., "meta": {"_type": "gradio.FileData"}}`。
- **API 端点要从 `/gradio_api/info` 取**：`/config` 的 `dependencies` 里还混着 Gradio
  内部 lambda，取第一个会调到无关函数（表现为只返回 visible 更新、不产出音频）。
- **开了网络加速/代理工具后，应用可能突然起不来**：`hf_hub_download` 即使命中本地缓存
  也会先发一个 HEAD 请求校验，若加速工具对 HF 流量做 TLS 拦截，就会抛
  `SSLCertVerificationError: unable to get local issuer certificate` 导致启动失败。
  权重已全部缓存，故 `run_webapp.ps1` 已加 `HF_HUB_OFFLINE=1` / `TRANSFORMERS_OFFLINE=1`
  强制离线，彻底规避。
- **参考音频分离人声：实测收益很小**【实测】。念山AI 已提供「参考音频也分离人声」
  勾选项（带伴奏的参考先经 Demucs 分离再提取音色）。但在真实歌曲片段上实测：
  分离与不分离的输出音色相似度分别为 0.2857 / 0.2955（差 -0.0098，属噪声范围），
  两个输出彼此相似度 0.892（几乎一致）。原因是 Seed-VC 用的 **CAM++ 说话人嵌入
  对伴奏相当鲁棒**（混音 vs 干净人声的嵌入相似度仍有 0.8322，即便该片段伴奏能量
  达到人声的 73%）；且我们关闭了 `auto_f0_adjust`，参考音频的 F0 基本不参与输出。
  **仍值得勾选的场景**：伴奏极响（鼓点密集段）、含混响/和声/对唱其他人声。
  代价很低（25 秒参考约 +5~8 秒）。

## 4. 日常使用

### 4.1 一条命令完成歌声转换

```powershell
cd 'F:\ai music\seed-vc'
.\run_svc.ps1 -Source <待转换人声.wav> -Target <目标音色参考.wav> -DiffusionSteps 30
```

脚本会自动处理：代理/镜像选择、缓存重定向、fbank 修复、显存采样，并在结束时给出判定。

| 参数 | 值 | 说明 |

| `--f0-condition` | **True** | 歌声转换必须开（对输出音高做调节）|

| `--fp16` | True | 半精度 |
| `--target` | — | 1~30 秒清晰、无伴奏、无噪音的参考音频 |

## 5. 显存的实测结论

### 5.1 扩散步数不影响显存（修正了一个常见误解）

在同一段 20.8 秒音频上对比【实测】：

| 扩散步数 | 显存峰值 | RTF |
|---|---|---|
| 30 | 3907 MiB | 1.79 |
| 15 | 3889 MiB | 1.28 |

峰值只差 18 MiB（0.5%），但速度快了 28%。**扩散步数只影响计算时间，不影响显存占用**——
显存由模型权重和固定尺寸的激活缓存决定（代码中 `setup_caches(max_seq_length=8192)` 会预分配）。

### 5.2 音频长度影响也很小【实测】

| 输入长度 | nvidia-smi 峰值 | PyTorch 实际分配 | RTF |
|---|---|---|---|
| 8.0 s | 3311 MiB | — | 1.25 |
| 20.8 s | 3885 MiB | 2680 MiB | 1.69 |
| 41.7 s | 3903 MiB | 2706 MiB | 1.38 |

从 20.8 秒到 41.7 秒（翻倍），实际分配只增加 26 MiB。

### 5.3 真正的缓解手段

按有效性排序：

1. **关闭占用显存的程序**（浏览器、微信、播放器）。本机空闲基线就有 240 MiB。
2. **分段处理超长音频**——虽然长度影响小，但极长输入仍会缓慢增长。
3. **降低 `--diffusion-steps`**——**只为提速，不为省显存**。

## 6. 效果验证（客观指标）

用合成的单声部素材做验证：源 20.8 秒（人声化音色），参考 10.8 秒（簧片音色）。

| 指标 | 结果 | 含义 |
|---|---|---|
| 旋律保留：半音平均误差 | **0.80 半音** | 旋律基本忠实 |
| 旋律保留：f0 相关系数 | 0.761 | 音高轨迹高度一致 |
| 音高中位数 | 506.9 → 501.1 Hz | 音高未被改写 |
| 音色迁移：频谱质心 | 2397 → **3644** Hz（参考 4298） | 距源 1247 Hz、距参考仅 654 Hz |

**结论**：旋律被保留、音色确实向参考音色迁移——这正是歌声转换应有的行为。

## 7. 客观预期（不要期望过高）

**能做到**
- 目标音色的音色特征（音高范围、共鸣、音质粗细）能被迁移，听感上"像"
- 零样本即可出可用结果，微调后相似度明显提升
- 44.1kHz 输出，可直接进入混音

**做不到 / 有明显损失**
- **不是完美复刻**。零样本相似度 < 微调 < 大量数据的训练式模型
- **演唱技巧难以迁移**：颤音、气声、真假声转换、情感处理主要学音色，学不到唱功
- **长句可能音准漂移或咬字模糊**
- **参考音频的干净程度直接决定质量上限**
- 验证用的是合成素材。**真实人声（尤其带混响/噪声）的效果需要用你的素材实测**

Web 界面勾选「🎵 源音频是完整歌曲」后自动执行三段流程：

```
原曲.mp3 ──1.Demucs分离──> vocals.wav + accompaniment.wav
          ──2.换音色(Seed-VC)──> vocals_converted.wav
          ──3.混音(峰值规整0.95)──> 成品.wav
```

【实测】（30 秒歌曲片段，步数 30，应用常驻显存约 3GB 状态下）：

| 指标 | 数值 |
|---|---|
| 分离耗时 | 18.6 秒（独立进程测 7.5 秒，应用内首跑含 CUDA 初始化） |
| 转换耗时 | 52.8 秒（RTF 1.76） |
| 全卡显存峰值 | 3856 MiB < 4096 ✔（分离阶段叠加 Seed-VC 常驻后） |
| 产出 | 纯人声(单声道) + 成品混音(立体声，伴奏保留) |

- 分离模型：demucs 4.1.0 的 `htdemucs`（80 MB，缓存于 `checkpoints\torch_hub`，
  需 `TORCH_HOME` 指到 F 盘，默认写 C 盘用户目录会失败——`app_nianshan.py` 已内置该设置）。
- demucs 用 uv 安装（venv 无 pip 模块：`uv pip install --python .venv\Scripts\python.exe demucs`）。
- 输出两份：「🎵 成品混音」（人声+伴奏，可直接当歌听）和「🎧 转换后人声」（纯人声干声）。

## 9. 风险与合规

- **克隆真人声音，尤其歌手，涉及人格权与版权**。中国《民法典》第 1023 条对自然人声音
  提供参照肖像权的保护，使用他人声音需**明确授权**。
- 商业用途需额外授权：Applio 仓库 README 明确要求用户尊重版权、知识产权与隐私权。
- 平台侧：多数音乐平台对 AI 克隆人声有审核规则。
- **安全做法**：用自己的声音、已获授权的素材，或虚拟/合成音色。技术方案对三者完全通用。
