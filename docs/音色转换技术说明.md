# 音色转换（Seed-VC）技术说明

> 本文档说明念山AI 音色转换引擎的工作方式、参数含义与实测数据。
>
> 证据标注：**【实测】** = 在 RTX 3050 Laptop（4 GB 显存）上实测；**【官方】** = 上游文档原文；**【推算】** = 估计值。

---

## 1. 引擎与处理链路

采用 **[Seed-VC](https://github.com/Plachtaa/seed-vc)** 的零样本歌声转换（SVC）模型。

| 环节 | 组件 | 作用 |
|---|---|---|
| 内容编码 | Whisper-small | 提取语义/内容表示 |
| 音色嵌入 | CAM++ | 从参考音频提取说话人音色（192 维）|
| 音高提取 | RMVPE | 提取源音频 F0，用于音高条件 |
| 生成 | DiT（扩散 Transformer）| 在内容 + 音色 + 音高条件下生成梅尔谱 |
| 波形重建 | BigVGAN v2 44 kHz | 梅尔谱 → 44.1 kHz 波形 |

**为什么用零样本方案**：不需要预先训练即可用 1~30 秒参考音频出结果，部署门槛低；
上游也支持微调（每位说话人至少 1 条语音、最少 100 步）进一步提升相似度。

### 完整歌曲模式

勾选后自动执行三段流水线：

```
原曲.mp3 ──1. Demucs 分离──> vocals.wav + accompaniment.wav
          ──2. Seed-VC 换音色──> vocals_converted.wav
          ──3. 混音（峰值规整 0.95）──> 成品.wav
```

分离模型为 **Demucs 4.1.0 `htdemucs`**（约 80 MB），与 Seed-VC 共用同一块 GPU。

## 3. 参数含义

| 参数 | 推荐值 | 说明 |
|---|---|---|
| F0 条件 | **开** | 歌声转换必须开，否则无法对输出音高做条件控制 |
| **自动 F0 调整** | **关** | **歌声转换必须关闭**：开启会把源音高整体移调，导致歌声与伴奏调性不一致【官方】 |
| 扩散步数 | **30~50** | 官方推荐歌声用 30~50；**只影响音质与耗时，不影响显存**（见 §4.1）|
| 音调变换 | 0 | 半音数移调，用于匹配伴奏调性 |
| 长度调整 | 1.0 | 语速/时长调整，小于 1 加速 |
| CFG 强度 | 0.7 | 对结果影响细微 |
| 参考音频 | — | **1~30 秒、清晰、无伴奏、无噪音**的人声 |

## 4. 实测性能与显存

### 4.1 扩散步数不影响显存

在同一段 20.8 秒音频上对比【实测】：

| 扩散步数 | 显存峰值 | RTF |
|---|---|---|
| 30 | 3907 MiB | 1.79 |
| 15 | 3889 MiB | 1.28 |

峰值只差 18 MiB（0.5%），但速度快了 28%。**扩散步数只影响计算时间，不影响显存占用**——
显存由模型权重与固定尺寸的激活缓存决定（代码中 `setup_caches(max_seq_length=8192)` 会预分配）。

### 4.2 音频长度影响也很小【实测】

| 输入长度 | nvidia-smi 峰值 | PyTorch 实际分配 | RTF |
|---|---|---|---|
| 8.0 s | 3311 MiB | — | 1.25 |
| 20.8 s | 3885 MiB | 2680 MiB | 1.69 |
| 41.7 s | 3903 MiB | 2706 MiB | 1.38 |

从 20.8 秒到 41.7 秒（翻倍），实际分配只增加 26 MiB。

> **重要澄清**：`nvidia-smi` 显示接近满卡**不代表要爆**。PyTorch 的缓存分配器会预留接近整卡的显存，
> 而实际分配只需约 2.7 GB。真正的失败信号是 `out of memory` 报错，不是高读数。

### 4.3 完整歌曲流水线【实测】

条件：30 秒歌曲片段，30 步，应用常驻显存约 3 GB。

| 指标 | 数值 |
|---|---|
| 分离耗时 | 18.6 秒（独立进程测 7.5 秒；应用内首跑含 CUDA 初始化）|
| 转换耗时 | 52.8 秒（RTF 1.76）|
| 全卡显存峰值 | 3856 MiB < 4096 ✔（分离阶段叠加 Seed-VC 常驻后）|
| 产出 | 纯人声（单声道）+ 成品混音（立体声，伴奏保留）|

实测一首 4 分钟歌曲（分离 + 分段转换 + 混音）总耗时约 **10.5 分钟**。

### 4.4 参考音频分离的实际收益很小【实测】

界面提供「参考音频分离人声」选项（带伴奏的参考先经 Demucs 分离再提取音色）。
但在真实歌曲片段上的 A/B 实测：

| 指标 | 值 |
|---|---|
| 分离参考的输出 vs 干净人声真值 | 0.2857 |
| 未分离参考的输出 vs 干净人声真值 | 0.2955 |
| 两者差异 | -0.0098（噪声范围）|
| 两个输出的彼此相似度 | 0.892（几乎一致）|

**原因**：CAM++ 说话人嵌入对伴奏相当鲁棒——即使该片段伴奏能量达到人声的 73%，
混音与干净人声的嵌入相似度仍有 **0.8322**；且关闭 `auto_f0_adjust` 后，
参考音频的 F0 基本不参与输出。

**仍值得勾选的场景**：伴奏极响（鼓点密集段）、含混响/和声/对唱其他人声。
代价很低（25 秒参考约增加 5~8 秒）。

## 5. 效果验证（客观指标）

用合成的单声部素材验证：源 20.8 秒、参考 10.8 秒【实测】。

| 指标 | 结果 | 含义 |
|---|---|---|
| 旋律保留：半音平均误差 | **0.80 半音** | 旋律基本忠实 |
| 旋律保留：F0 相关系数 | 0.761 | 音高轨迹高度一致 |
| 音高中位数 | 506.9 → 501.1 Hz | 音高未被改写 |
| 音色迁移：频谱质心 | 2397 → **3644** Hz（参考 4298）| 距源 1247 Hz、距参考仅 654 Hz |

**结论**：旋律被保留、音色确实向参考迁移——这正是歌声转换应有的行为。

### 扩散步数会不会让音色更像？

用 Seed-VC 自身的 CAM++ 模型测量输出与参考的音色相似度【实测】：

| 步数 | 耗时 | 音色相似度 | 8 kHz 以上能量 |
|---|---|---|---|
| 8 | 6.1 s | 0.6328 | 3.58%（有噪声）|
| 15 | 6.2 s | 0.6645 | 3.75%（有噪声）|
| 30 | 8.2 s | 0.6234 | 1.90% |
| 50 | 12.4 s | 0.6611 | 2.16% |
| 80 | 16.8 s | 0.6668 | **1.73%（≈ 参考音频）** |

**音色相似度在 0.623~0.667 之间波动，没有单调趋势。** 加步数的真实作用是
**减少高频伪影**（8~15 步有明显噪声，30 步以上趋于稳定），而不是让音色更像。

> **测量局限**：本测试用合成素材，且 CAM++ 是语音说话人模型，对歌声音色的敏感度有限。
> 最终仍应以听感判断。

## 6. 客观预期

**能做到**

- 目标音色的特征（音高范围、共鸣、音质粗细）能被迁移，听感上"像"
- 零样本即可出可用结果；微调后相似度明显提升
- 44.1 kHz 输出，可直接进入混音

**做不到 / 有明显损失**

- **不是完美复刻**。相似度：零样本 < 微调 < 大量数据的训练式模型
- **演唱技巧难以迁移**：颤音、气声、真假声转换、情感处理——学到的是音色，不是唱功
- **长句可能音准漂移或咬字模糊**
- **参考音频的干净程度直接决定质量上限**

**真正能提升相似度的杠杆**（按影响排序）

1. 参考音频质量（干净、无伴奏、无混响、5~30 秒）
2. 参考音频的音域与源接近（差异大时音色会走样）
3. 调性匹配（`pitch_shift` 正确）
4. **微调**——提升相似度的根本手段，需要目标声音的素材

## 7. 部署与兼容性说明

### 7.1 依赖清单的调整

上游 `requirements.txt` 需三处处理，处理后的清单为
[`app/requirements-infer.txt`](../app/requirements-infer.txt)：

1. **删掉指向 nightly 源的前几行**——会覆盖正确的 CUDA 版本
2. **删掉 `torch` / `torchvision` / `torchaudio`**——避免从 PyPI 抓到 CPU 版覆盖已安装的 CUDA 版
3. **删掉 `resemblyzer`**——它依赖需要 C 编译的 `webrtcvad`，是 Windows 上最常见的失败点；
   经代码核查它**只被 `eval.py` 用到**，推理流程不需要

### 7.2 已修复的上游兼容性问题

**`torchaudio.compliance.kaldi.fbank` 在 CUDA 上崩溃**【实测】：

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xc0 in position 117: invalid start byte
```

报错位置在 `torch.fft.rfft` 内部，看起来像 FFT 问题，实际不是。逐项界定后：

| 操作 | CPU | CUDA |
|---|---|---|
| `torch.fft.rfft` | 正常 | 正常 |
| `torch.fft.fft` | 正常 | 正常 |
| `torch.stft` | 正常 | 正常 |
| **`kaldi.fbank`** | 正常 | **崩溃** |

该 `UnicodeDecodeError` 很可能是底层错误信息按 UTF-8 解码失败后抛出的"伪装错误"。

**处理**：把 fbank 强制放到 CPU 计算再搬回设备。fbank 只用于给 CAM++ 提取 80 维梅尔特征，
计算量极小，对结果无影响，且**不改动上游代码**（便于日后更新）。

**对上游的其他修改**（两处默认值）以补丁形式提供，见 [`patches/README.md`](../patches/README.md)。

## 8. 常见问题

| 现象 | 原因与处理 |
|---|---|
| 应用启动后报 `SSLCertVerificationError` | 代理/加速工具对 HuggingFace 流量做了 TLS 拦截。权重已缓存时会自动进入离线模式；未缓存则需可用的网络通道 |
| 权重反复下载到错误位置 | `app_svc.py` 使用相对路径（`./checkpoints/...`）。启动脚本已固定工作目录 `Set-Location`，自行调用时也须在项目目录内启动 |
| 含中文的 `.ps1` 报语法错误 | PowerShell 脚本必须保存为 **UTF-8 带 BOM**，否则会被按 ANSI 解析 |
| 输出 WAV 用 `wave` 库读不了 | 输出是 32 位浮点 WAV（subtype FLOAT），需用 `soundfile` 等库读取 |
| `nvidia-smi` 显示显存接近满 | 正常现象，见 §4.2。以是否出现 `out of memory` 为准 |
| 调 Gradio API 报 `The 'meta' field must be explicitly provided` | 文件入参必须是字典：`{"path": ..., "meta": {"_type": "gradio.FileData"}}` |
| 取 API 端点取到了无关函数 | 应从 `/gradio_api/info` 读取命名端点；`/config` 里混有 Gradio 内部 lambda |
| `Start-Process -ArgumentList` 启动失败 | 路径含空格时会被拆开，改用 `&` 直接调用 |

## 9. 风险与合规

- **克隆真人声音，尤其歌手，涉及人格权与版权**。中国《民法典》第 1023 条对自然人声音
  提供参照肖像权的保护，使用他人声音需**明确授权**。
- **平台侧**：多数音乐平台对 AI 克隆人声有审核规则。
- **安全做法**：使用自己的声音、已获授权的素材，或虚拟/合成音色。技术方案对三者完全通用。
- 面向公众提供生成式 AI 服务，在中国境内还需完成算法备案与安全评估，深度合成内容需标识。
  详见 [README 的许可证与合规一节](../README.md#许可证与合规)。
